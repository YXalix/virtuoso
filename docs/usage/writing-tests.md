# Writing Test Cases

`init` automatically discovers every executable under rootfs `/tests/` (including one level of
test-group subdirectories) — **adding a new case requires zero wiring**. Two hard rules:

- Tests must be **statically linked** (there is no dynamic loader inside the VM; `crt-static` is
  the rustc default for the musl target and the workspace recipe is frozen — case authors need not worry about it);
- **Using `|| true` to mask failures is forbidden**.

All cases live in a single cargo workspace (`infra/testcases/`): **coda (std
Rust) is the framework and entry point, and C test bodies are compiled by each case crate's
build.rs into the same static binary** (C over Rust). Protocol v1 treats Rust/C assertions
identically — the same serial console text, the same set of counters (C macros land back in
coda via FFI; a single source of truth for the frozen text).

## Creating a Test Case (Copy test-example)

1. Copy `infra/testcases/test-example/` to `test-<name>/` and change the crate's
   `name` in `Cargo.toml`. The workspace members list is a glob (`test-*`) — **no need to
   edit workspace files**. The crate name is the binary name and appears in the serial console
   line `--- Running: test-<name> ---`.

2. **Rust tests**: the case crate's `src/main.rs` registers
   `("name", fn() -> bool)` entries in `TESTS` and asserts with `coda::check!` (or the
   manual `pass!/fail!/skip!` composition). main is a single line — banner, panic hook, C-section
   invocation, counting, and the exit code all live in `coda::run_and_exit`:

```rust
use coda::{run_and_exit, TestCase};

fn my_feature() -> bool {
    // Drive the kernel under test via syscalls / /proc / /sys / /dev (std is available)
    coda::check!(!std::fs::read_to_string("/proc/uptime").is_err(), "…")
}

static TESTS: &[TestCase] = &[("my_feature", my_feature)];

fn main() {
    run_and_exit(TESTS);
}
```

3. **C tests**: put `.c` files under `c/` (build.rs collects and compiles them automatically)
   and assert with the macros from `coda.h` (`PASS/FAIL/SKIP/INFO`), calling each one from
   `run_c_tests`. An empty `c/` is fine too — an empty stub is compiled in automatically
   to hold the symbols:

```c
#include "coda.h"

static void test_my_feature(void)
{
    if (/* expected condition */)
        PASS("the thing happened");
    else
        FAIL("expected X, got Y");
}

void run_c_tests(void)
{
    test_my_feature();
}
```

4. Rebuild and run:

```bash
virtuoso build && virtuoso test --timeout 30
```

> IDE: the repo ships its own `.vscode/settings.json` (rust-analyzer indexes this workspace);
> on the C side, clangd consumes the `compile_commands.json` generated by each case crate (a single
> `cargo check` run produces it).

## Assertion Output Rules

- The test binary outputs only `[PASS]` / `[FAIL]` / `[SKIP]` / `[INFO]` assertion lines
  (always through the macros; never print protocol prefixes directly with `printf`/`println!`);
- `--- Running:` / `PASSED:` / `FAILED:` / `Test Results:` /
  `TEST_COMPLETE:` are **init's assembly-level markers**; test programs must not print them;
- The exit code is aggregated by coda (any FAIL > 0 → 1), and C-section counting shares the same
  source via FFI — case code never needs to manage counters or exit codes itself.

The protocol text is frozen; see [Frozen Contracts](../concepts/contracts.md) for line-by-line semantics.

## Tests That Need Kernel Modules

Module requirements go in the `[tests]` section of `virtuoso.toml` (the natural home when writing
test cases for a kernel feature — no need to attach them to unrelated components):

```toml
[tests]
require = ["overlay", "kvm"]   # "<module> [key=val ...]", always at the runtime stage
```

The builder merges `[tests].require` into the component union to generate the rootfs
`/lib/modules/modules.conf` (component entries for same-named modules take precedence; this only
fills the difference). VM-capability modules (passthrough, NUMA, pmem, etc.) still go through
[Component Mechanics](../concepts/components.md). For modules under iteration, prefer
`=m` over `=y` to avoid kernel rebuilds.

## Test Groups

A first-level subdirectory under `/tests/` is a test group: within a group, a case's name token
is `group/case` (shown in the serial console and verdict as `--- Running: smoke/test-net ---`);
flat binaries remain the default group. A group is purely a **file-layout dimension**;
marker protocol v1 text is unchanged.

Declare a case into a group — write it in the case crate's own `Cargo.toml` (the declaration
travels with the case; there is no central manifest):

```toml
[package.metadata.virtuoso]
group = "smoke"
```

- Crates without a declaration go flat into `/tests/` (backward compatible);
- Execution order within a group = lexicographic; between groups = lexicographic by directory name;
- The summary line `Test Results: N/M` is always the global tally.

## Adding Files to the rootfs (rootfs.d)

The repo-root `rootfs.d/` is the user drop-in directory (git-ignored, not shipped with a clone):
at build time the whole tree is **merged additively** into the rootfs (directory-level union),
suitable for test data, pre-seeded scripts, and environment files.
**Additive-only (never overwrites)** — any file colliding with a path produced by the builder's
assembly is a build-time error, so framework files (init, the module manifest, the busybox tree)
can never be shadowed. The directory absent by default = the build is a no-op; the first
`virtuoso doctor` run creates the empty directory automatically, and you can also create it
yourself anytime.

Dropping in a script case is adding a test: `rootfs.d/tests/<group>/run-foo.sh` (executable bit
set); init judges PASSED/FAILED by exit code — same protocol and same verdict handling as
compiled cases.

## Running Only Some Test Cases (Faster Iteration)

```bash
virtuoso test --only test-myfeature          # single (flat)
virtuoso test --only smoke/test-net          # single (within a group)
virtuoso test --only smoke/                  # whole group (trailing slash)
virtuoso test --only test-a,test-b           # comma-separated
```

`--only` reaches init via the kernel cmdline and runs only the manifest entries; the marker
protocol v1 is unchanged (selected cases emit the full marker set as usual). Zero manifest hits
(a misspelled name) is judged as a failure outright — no 0/0 false green.
