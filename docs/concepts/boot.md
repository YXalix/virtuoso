# Two-Stage Boot

> **A complete reference for future maintainers (AI included)**: the
> architecture of the two-phase startup, the in-VM execution flow, the dual
> module manifest rule, known kernel quirks, and "for a common change, which
> file should I touch".
>
> Prerequisite: this chapter assumes you know what QEMU
> `-kernel`/`-initrd`/`-drive` are. For where the images come from, see
> [Provisioning and Build Pipeline](pipeline.md).

## 1. Two-Phase Startup

```
qemu-system-<arch>
  ├─ -kernel  Image                              kernel under test
  ├─ -initrd  initrd.img      ── Phase 1 ──      minimal initramfs (memory disk)
  │            PID 1 = /init (= infra/init-initramfs)
  │            ① mount proc/sys/dev (with quirk fallbacks, see §4)
  │            ② insmod every .ko in modules-boot.conf (only what it takes to "reach the root disk")
  │            ③ mount root=/dev/vda
  │            ④ exec switch_root /mnt /init
  │
  └─ -drive  rootfs.img       ── Phase 2 ──      ext4 system disk (virtio → /dev/vda)
               PID 1 = /init (= infra/init, the test init)
               ① idempotently re-mount proc/sys/dev (mostly already mounted after switch_root)
               ② insmod every .ko in modules.conf (generated from the component require union, /lib/modules/)
               ③ interactive shell (default) or auto_test: run /tests/* → poweroff
```

**Why two phases**: the kernel under test (openEuler) builds
`CONFIG_VIRTIO_BLK`/`CONFIG_EXT4_FS` as modules (`=m`). A bare ext4 root runs
into the deadlock of "the mount driver sits on the disk, but the disk needs
the driver before it can be mounted". Loading the drivers into the initramfs
in memory first is the only way out — which is also standard distro practice.

**Responsibility boundary (remember this line; changing things in the wrong
place is the biggest risk)**:

| | initramfs (Phase 1) | rootfs (Phase 2) |
|---|---|---|
| Sole mission | get `root=` mountable | run tests / provide an interactive environment |
| Contents | busybox + **boot modules** + pivot init | busybox + **test modules** + test init + /tests (group subdirectories) + rootfs.d increment |
| Lifecycle | memory freed after switch_root | persistent ext4; loop mount and modify freely |
| Change cadence | when the kernel or boot modules change | when tests are added or the test flow changes |

## 2. In-VM Execution Flow

### Phase 1: `infra/init-initramfs` (busybox ash, POSIX syntax)

Does one thing only: **get `root=` mountable, then switch_root**.
Deliberately contains no test logic.

```
mount proc/sys/devtmpfs/tmpfs          # all failures tolerated via 2>/dev/null
mknod console/null + mdev -s           # quirk fallback A (see §4), do not remove
insmod modules-boot.conf line by line  # best-effort; a failure only WARNs
parse root= from /proc/cmdline (default /dev/vda)
poll [ -b $ROOT ] for up to 10s        # virtio async probing has latency
if [ ! -b ], mknod from /proc/partitions   # quirk fallback B (see §4), do not remove
mount -o rw $ROOT /mnt || emergency shell
exec switch_root /mnt /init            # busybox moves the /proc /sys /dev mounts into the new root
```

### Phase 2: `infra/init` (the test init, PID 1 after entering the rootfs)

- `mount_filesystems`: re-mount proc/sys/dev/devpts/shm — **must be
  idempotent** (mostly already mounted after switch_root; swallow the
  errors); it also guarantees the rootfs can bootstrap itself when booted
  directly (kernels with the root driver `=y`, no initramfs);
- `load_modules`: insmod the test modules from the rootfs's
  `/lib/modules/modules.conf`; line format `<module> [key=val ...]`
  (parameters passed through to insmod as-is);
- no cmdline `auto_test` → `setsid cttyhack /bin/sh` interactive shell;
  with it → run `/tests/*` in order, aggregate `Test Results: N/M` +
  `TEST_COMPLETE: ALL/SOME TESTS FAILED/PASSED` (CI asserts on this marker) →
  `poweroff -f`.

## 3. The Dual Module Manifest Rule

| Manifest | Semantics | Goes to | Loaded by | Source |
|---|---|---|---|---|
| `infra/modules-boot.conf` | the minimal set that makes `root=` mountable (**frozen base set, hand-maintained**) | initramfs `/lib/modules/` | `init-initramfs`, before the pivot | hand-written conf file |
| component `stage = "boot"` additions | something a component needs available early in boot | same as above (appended after the base set) | same as above | `virtuoso.toml` `[components.*] require` |
| generated `modules.conf` | every module need of the enabled components | rootfs.img `/lib/modules/` | `infra/init`, after the pivot | the component require union (generated by the builder) |

**Decision rule: does this module have to be in the kernel "before root is
mounted"? Yes → give the component `stage = "boot"`; no → the default
runtime.** A require entry = a conf line `"<module> [key=val ...]"`; the union
dedupes by first token keeping the first occurrence, in the fixed component
order, and entry order is the insmod order (dependencies first). A missing
`.ko` fails the build.

For the component mechanism overview, see [Components](components.md).

## 4. Known Kernel Quirks and Required Workarounds (Do Not Remove!)

Found by hands-on testing against the openEuler kernel + modified QEMU (with
UBIOS logging). Removing any one of them brings back
`cannot mount root=/dev/vda` or a panic:

| # | Symptom | Root cause | Fallback (location) |
|---|---|---|---|
| A | `/dev` is empty inside the initramfs | devtmpfs mounts but does not auto-populate | `mknod console/null` + `mdev -s` (top of init-initramfs) |
| B | `/sys/class/block/vda/dev` is empty | the sysfs dev attribute outputs nothing | parse major:minor from `/proc/partitions`, then `mknod` (middle of init-initramfs) |
| C | bare ext4 root panics outright | `CONFIG_VIRTIO_BLK`/`CONFIG_EXT4_FS` = m | the two-phase architecture itself (§1) |
| D | busybox 1.36.1 `tc` applet fails to build | incompatible with kernel headers ≥ 6.8 | `sed` CONFIG_TC off in CI (workflow) |

## 5. Modification Playbook

**Add a test module** (most common)
→ add/enable a `require` on the corresponding component in `virtuoso.toml`
(mind dependency order, dependencies first), then `virtuoso build`. **Do not**
touch `modules-boot.conf` — that would change initrd.img needlessly.

**Add a test case** → see [Writing Test Cases](../usage/writing-tests.md);
change the test flow → change `infra/init`. Verify with:
`virtuoso build && virtuoso test --timeout 30`.

**Add files to the rootfs** (test data, script cases, environment files)
→ put them in `rootfs.d/` at the repo root; at build time the whole tree is
merged incrementally into the rootfs. **Additive-only (never overwrites)**:
a path colliding with an assembled artifact = build-time error;
`rootfs.d/tests/<group>/run-x.sh` is a script case (judged by exit code).
See [Writing Test Cases](../usage/writing-tests.md) for details.

**In-VM environment customization** (e.g. pre-allocating huge pages)
→ write a generic customization as an `init-hooks.sh` snippet (the builder
injects rootfs `/init-hooks.sh`, the init side sources it behind a guard,
after devtmpfs is mounted and before insmod/agent startup):

  ```sh
  mkdir -p /mnt/huge
  mount -t hugetlbfs nodev /mnt/huge
  echo 20 > /sys/kernel/mm/hugepages/hugepages-2048kB/nr_hugepages
  ```

**Change pivot / early-loading behavior**
→ change `infra/init-initramfs`. Hold two lines: do only what it takes to
"reach root="; POSIX/busybox-ash syntax (local check:
`busybox sh -n infra/init-initramfs`). After changing, re-run the §6
verification playbook.

**Swap the rootfs distro** (e.g. Alpine/debootstrap)
→ rootfs.img is just a plain ext4. Change the builder's rootfs assembly
section, or loop mount it outside the VM and replace the contents. The
two-phase startup chain needs no changes at all.

**Release a new busybox version** → trigger `busybox-release` manually from
Actions (fill in the version), then in `virtuoso.toml` set
`[busybox] version = <ver>`.

**Change the release rootfs /init**
→ in principle, don't (a frozen invariant, see
[Provisioning and Build Pipeline](pipeline.md)). If you truly must: edit the
printf section in the workflow and re-run it. **Use printf, not a heredoc** —
YAML block scalar indentation stripping makes the `EOF` terminator mismatch
(dash's `<<-` only accepts tabs, and YAML forbids tabs); CI will report
`syntax error: end of file unexpected`.

**General rules for shell scripts**: GitHub Actions runs `run:` with dash —
`local a=1 b=$a` with same-line cross references yields empty values (must be
split across lines), brace expansion (`{a,b}`) is unsupported, and `${@:2}` is
unsupported (use `shift`). In-VM scripts (`init`, `init-initramfs`) are
busybox ash; likewise write POSIX, and run a `busybox sh -n` syntax check
after changing.

## 6. Verification Playbook (Run After Every Change)

```bash
# 0. Syntax
busybox sh -n infra/init-initramfs && busybox sh -n infra/init

# 1. Build
virtuoso build

# 2. Interactive mode: you should see [initramfs] module logs → root mount → test init banner → ~ # shell
virtuoso shell

# 3. Automated tests: should print TEST_COMPLETE: ALL TESTS PASSED and shut down cleanly (exit 0)
virtuoso test --timeout 30
```

When you need to drive QEMU directly, bypassing virtuoso, for troubleshooting
(equivalent form):

```bash
qemu-system-aarch64 -M virt -cpu cortex-a72 -m 1G -nographic -no-reboot \
  -kernel $KERNEL_PATH/arch/arm64/boot/Image -initrd target/artifacts/initrd.img \
  -drive file=target/artifacts/rootfs.img,format=raw,if=virtio \
  -append "console=ttyAMA0 root=/dev/vda rw init=/init loglevel=3"
```
